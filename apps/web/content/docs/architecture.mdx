title: How the Worker works
description: The request path, Cloudflare bindings, and image data handling.
---

```text
Your backend
  | POST image + Bearer API key
  v
nobg Worker (Hono)
  | authenticate, rate-limit, validate
  v
Cloudflare Images binding
  | segment: foreground
  v
Transparent PNG or WebP returned to your backend
```

## Request lifecycle

1. Assign a request ID and disable response caching.
2. Verify the configured Bearer API key using a timing-safe digest comparison.
3. Check the Cloudflare rate limiter.
4. Read the upload with a bounded body size and parse multipart fields.
5. Validate the image signature, declared format, file size, and pixel count.
6. Send the bytes through the Images binding using `segment: "foreground"`.
7. Return the binary image with a download filename.

The service uses the [Cloudflare Images binding](https://developers.cloudflare.com/images/optimization/binding/) to process uploaded bytes without a public image URL. Background removal uses [foreground segmentation](https://developers.cloudflare.com/images/optimization/features/#segment).

## Data handling

nobg does not save uploads or outputs to R2, D1, KV, or Cloudflare Images storage. It buffers a bounded upload for validation and returns the processed stream with `Cache-Control: no-store`. Cloudflare processes the bytes under its service policies.

Unexpected application errors log an event name and request ID. These logs do not include image bytes, filenames, keys, or provider error messages. Cloudflare may record platform request metadata through observability.

## Deployment contents

`apps/api/src/index.ts` contains the handler. `apps/api/wrangler.jsonc` declares its Images and rate limiter bindings. `packages/contracts` supplies formats, limits, and error types used by the handler and OpenAPI document.

This is a single Worker deployment. There is no dependency on the documentation website at runtime.
